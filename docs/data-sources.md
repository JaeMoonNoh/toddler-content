# 데이터 출처

혜택 데이터는 공공데이터포털(data.go.kr)의 API 세 개에서 받는다. 인증키는 계정당 하나이고 세 API에 같은 키를 쓴다.
키는 `apps/api/.env`의 `DATA_GO_KR_SERVICE_KEY`에만 둔다 (git 제외).

조사일: 2026-11-02

## 1. 보조금24 (주 출처)

- 기본 주소: `https://api.odcloud.kr/api/gov24/v3`
- `serviceList`: 목록. 서비스명, 지원대상, 선정기준, 지원내용, 신청방법, 신청기한, 소관기관, 수정일시 등
- `serviceDetail`: 상세. 구비서류, 법령, 자치법규, 온라인신청사이트URL 등이 추가됨
- `supportConditions`: 서비스별 대상 조건 코드
- 페이지당 최대 1,000건 → 전체 수집은 엔드포인트별 11번 호출
- 필터: `cond[수정일시::GTE]=20261101000000` 처럼 **수정된 것만** 받을 수 있다 → 매일 변경 감지에 사용

조건 코드 중 우리가 쓰는 것:

| 코드 | 뜻 |
|---|---|
| JA0301 | 예비부모/난임 |
| JA0302 | 임산부 |
| JA0303 | 출산/입양 |
| JA0110, JA0111 | 대상 연령 시작, 끝 |
| JA0411 | 다자녀가구 |
| JA0201~JA0205 | 중위소득 구간 (0~50%, ~75%, ~100%, ~200%, 200% 초과) |

## 2. 복지로 중앙부처 (보완 출처)

- 목록: `https://apis.data.go.kr/B554287/NationalWelfareInformationsV001/NationalWelfarelistV001?callTp=L&srchKeyCode=001&pageNo=1&numOfRows=500`
- 보조금24에 이름으로 검색되지 않는 **부모급여 지원**, **모성보호육아지원(출산전후휴가·육아휴직 급여)** 이 여기에는 있다.

## 3. 복지로 지자체 (보완 출처)

- 목록: `https://apis.data.go.kr/B554287/LocalGovernmentWelfareInformations/LcgvWelfarelist?ctpvNm=충청북도&pageNo=1&numOfRows=500`
- 청주시 항목은 `sggNm`에 "청주시"가 들어간 것. 충북 302건 중 청주 28건.

## 후보를 고르는 방법

1. 지역: 보조금24는 `소관기관명`에 "청주"가 있으면 청주, 정확히 "충청북도"면 충북, `소관기관유형`이 중앙행정기관·공공기관이면 전국.
   복지로 지자체는 `sggNm`이 청주시면 청주, 비어 있으면 충북.
2. 관련성:
   - **강함**: 서비스명에 임신·출산·영유아 관련 단어가 있거나, 임신·출산 코드(JA0301~0303)가 붙어 있으면서 다른 대상 코드가 거의 없는 것
   - **후보**: 임신·출산 코드는 붙어 있지만 대상이 넓고, 지원대상 설명에 관련 단어가 있는 것
3. 같은 혜택이 두 출처에 모두 있으면 이름을 정규화해서 한 줄로 합친다.

결과: [research/2026-11-02-cheongju-candidates.md](research/2026-11-02-cheongju-candidates.md) (155건)

## 주의할 점

- **조건 코드와 생애주기 값은 넓게 붙어 있다.** "누구나 대상"인 서비스(예: 근로·자녀장려금)도 임산부 코드가 Y이고, 휠체어 수선비에도 "영유아"가 붙어 있다. 코드만으로 거르면 3,960건이 나와서 쓸 수 없다. 이름·설명 키워드와 함께 판단하고, 최종 포함 여부는 사람이 정한다.
- **한 출처로는 부족하다.** 보조금24에 부모급여가 없고, 복지로에는 상세 정보(선정기준, 신청기한)가 적다. 두 출처를 함께 받고 같은 혜택끼리 연결해야 한다.
- 금액은 대부분 `지원내용` 문장 안에 있다. 금액을 숫자로 쓰려면 사람이 확인해서 입력해야 한다.

## 변경 감지

코드: `apps/api/src/collect/` — `domain/snapshot-diff.ts`(무엇을 변경으로 보는가), `application/apply-snapshot.use-case.ts`·`collection-policy.ts`(수집 반영 흐름과 정책), `infrastructure/prisma-snapshot.repository.ts`(DB 저장)

| 테이블 | 내용 |
|---|---|
| `SourceItem` | 출처 + 출처 ID별 최신 원본(`payload`), 비교용 지문(`hash`), 목록에서 사라진 시각(`removedAt`) |
| `SourceChange` | 수집 한 번에서 발견한 추가 / 변경 / 삭제. 변경이면 `changedFields`에 `{ field, before, after }` |
| `CollectionRun` | 출처별 수집 실행 기록. 상태, 건수, 오류 |

동작 규칙:

- 출처의 **전체 목록**을 받아 저장된 원본과 비교한다. 보조금24는 `수정일시` 필터로 바뀐 것만 받을 수도 있지만, 삭제는 전체 목록을 받아야 알 수 있어서 하루 한 번 전체를 받는다 (보조금24 호출 22번, 한도 안).
- 지문은 키 순서와 상관없이 같은 내용이면 같게 나오도록 계산한다. **매일 바뀌는 필드는 비교에서 뺀다** (보조금24 `조회수`, 복지로 `inqNum`). 빼지 않으면 매일 수천 건이 "변경"으로 잡힌다.
- **첫 수집은 기준점만 저장**하고 변경 기록은 남기지 않는다.
- 사라졌던 항목이 다시 나타나면 "추가"로 기록한다.
- 받은 항목이 **0건이거나 이전보다 10% 넘게 줄면 수집을 중단**하고 실패로 기록한다. API 장애로 목록이 일부만 왔을 때 대량 삭제로 오인하지 않기 위해서다.

실제 보조금24 데이터 10,942건으로 확인한 결과: 첫 수집 1.1초, 이후 수집 0.3초.

## 수집기

코드: `apps/api/src/collect/infrastructure/sources/` (출처별 fetcher), `cli/` (수동 실행), `scheduling/` (자동 실행)

| 출처 | 클래스 | 한 번에 받는 건수 | 하루 전체 수집 호출 수 (2026-11-02 기준) |
|---|---|---|---|
| 보조금24 | `Gov24Fetcher` | 1,000 | 11 |
| 복지로 중앙부처 | `BokjiroNationalFetcher` | 500 | 1 |
| 복지로 지자체 | `BokjiroLocalFetcher` | 500 | 10 |

- 실행: `pnpm collect` 또는 매일 새벽 4시(한국 시각) 자동 실행. 수집이 끝나면 혜택 검토 요약을 함께 보여준다 (`apps/api/src/daily-check/`).
- 출처는 차례로 수집하고, **한 출처가 실패해도 나머지는 계속한다.** 실패도 `CollectionRun`에 이유와 함께 남는다.
- 같은 수집이 겹치면 나중 것은 건너뛴다.
- 요청은 시간 초과 30초, 5xx·429·네트워크 오류만 최대 2번 재시도한다. 4xx(인증키 오류 등)는 바로 실패한다.
- 목록이 중간에 잘리거나(빈 페이지, 건수 부족), ID 없는 항목이 있으면 그 출처의 수집을 실패로 처리한다. 잘못된 목록으로 삭제가 기록되지 않게 하기 위해서다.
- 공공데이터포털 오류는 HTTP 403 + XML로 오기도 하고, HTTP 200 + XML(`OpenAPI_ServiceResponse`)로 오기도 한다. 둘 다 실패로 본다.
- 오류 메시지와 DB 기록에서 인증키는 `serviceKey=***`로 가린다.

새 출처를 추가하려면 `PagedSourceFetcher`를 상속해 "한 페이지 가져오기"와 "항목 → 원본 변환"만 구현하고, `CollectModule`의 fetcher 목록에 넣는다.

실제 수집 결과 (2026-11-02): 세 출처 16,231건 첫 수집 16초, 바로 다시 수집했을 때 변경 0건 (조회수 무시가 실제 데이터에서도 동작).

## 검토와 게시

코드: `apps/api/src/benefit/` — `domain/benefit.ts`(검토 상태 규칙), `application/`(목록 반영, 검토 대기열, 확인, 게시 목록), `infrastructure/`(목록 파일, DB, 명령, API)

혜택 목록은 `apps/api/data/benefit-catalog.json`에 있다 (조사에서 확정한 112건). 혜택마다 근거가 되는 공공 API 원본을 하나 이상 연결하고, 첫 번째가 대표 출처다.

| 테이블 | 내용 |
|---|---|
| `Benefit` | 사이트에 올리는 혜택. 이름, 지역, 원문 링크, 사람이 마지막으로 확인한 시각(`verifiedAt`) |
| `BenefitSource` | 혜택이 근거로 삼는 원본(출처 + 출처 ID)과, 확인할 때의 원본 지문·내용 |

검토 상태는 저장하지 않고, **확인할 때의 원본과 지금 수집된 원본을 비교해서** 그때그때 정한다. 그래서 수집기는 혜택을 몰라도 되고, 원본이 바뀌었다가 원래대로 돌아오면 자동으로 "확인됨"이 된다.

| 상태 | 뜻 | 사이트 |
|---|---|---|
| 확인됨 | 확인한 뒤로 원본이 그대로 | 게시 |
| 원본 바뀜 | 확인한 뒤로 원본이 바뀜 | 마지막 확인일과 함께 "다시 확인 중"으로 게시 |
| 확인 전 | 아직 확인하지 않았거나, 확인 뒤에 목록 파일에서 혜택 정보를 고침 | "검증 전"으로 게시 |
| 원본 사라짐 | 출처 목록에서 사라짐 (사업 종료일 수 있음) | 게시 멈춤 |
| 원본 없음 | 수집된 적 없는 ID를 가리킴 (목록 파일 오타 등) | 게시 안 함 |

- `GET /benefits`의 `reviewStatus`(`VERIFIED`, `UNVERIFIED`, `SOURCE_CHANGED`)로 화면이 표시를 정한다. 확인 전이면 `verifiedAt`은 `null`.
- 확인 전 혜택도 보여주는 이유: 원본이 정부 공식 데이터라 숨기는 것보다 "검증 전"으로 표시해 보여주는 게 낫다 (CLAUDE.md 제품 원칙). 확인은 시간 날 때 조금씩 한다.
- 원본이 바뀐 혜택을 바로 내리지 않는 이유: 문구 수정처럼 작은 변경도 많아서, 내리면 사이트에서 혜택이 자주 사라졌다 나타난다. 대신 확인일을 그대로 보여줘서 언제 기준 정보인지 알 수 있게 한다.
- 목록 파일에 문제가 하나라도 있으면 아무것도 반영하지 않는다. 목록에서 빠진 혜택은 DB에서 지우지 않고 알려만 준다.
- 사라졌거나 없는 원본은 확인할 수 없다. 목록 파일에서 연결을 고치거나 혜택을 빼야 한다.

## 신청 기간 규칙

혜택 목록 파일의 `schedule`에 적는다. 날짜는 사용자의 출산예정일로 **브라우저에서** 계산한다 (출산예정일은 서버로 보내지 않는다).

```json
"schedule": {
  "from":  { "anchor": "birth", "months": 0, "days": 0 },
  "until": { "anchor": "birth", "months": 0, "days": 59 },
  "untilLabel": "소급 신청 마감",
  "summary": "출생일 포함 60일 안에 신청해야 출생한 달부터 받아요",
  "basis": { "text": "근거가 된 원문 문장", "url": "https://..." }
}
```

- `anchor`: `pregnancy`(임신 시작 = 출산예정일 280일 전) 또는 `birth`(출생일. 태어나기 전에는 출산예정일로 계산)
- 개월을 먼저 더하고 일수를 더한다. 그 달에 없는 날이면 말일로 맞춘다 (1월 31일 + 1개월 = 2월 28일)
- 기한은 `신청기한` 필드에 "상시신청"으로만 있고 **`선정기준`이나 `지원대상` 안에 적혀 있기도 하다** (산모·신생아 건강관리). 규칙을 뽑을 때 세 필드를 모두 본다.
- **근거(`basis`)는 반드시 적는다.** 공공 API 원문에 있는 문장이면 그대로, 없으면 어디 기준인지 적는다
- 규칙을 바꾸면 그 혜택은 다시 "검증 전"이 된다

- 청주 셋째 자녀 양육지원금: 2022년 이전 출생아만 대상 (2023년부터 충북 출산육아수당으로 통합)

## 받기 위한 조건

혜택 목록 파일의 `conditions`에 적는다. 사용자의 답과 비교하는 건 **브라우저에서** 한다.

| 조건 | 뜻 | 혜택 |
|---|---|---|
| `BIRTH_PARENT_INSURED` | 출산하는 분이 고용보험 가입 | 출산전후휴가 급여, 예술인·노무제공자 출산전후급여 |
| `PARTNER_INSURED` | 배우자가 고용보험 가입 | 배우자 출산휴가 급여 |
| `EITHER_PARENT_INSURED` | 부모 중 한 명이라도 가입 | 육아휴직급여, 육아기 근로시간 단축 급여, 난임치료휴가 급여, 모성보호육아지원 |
| `BIRTH_PARENT_UNINSURED` | 출산하는 분이 고용보험 미가입 | 고용보험 미적용자 출산급여 |
| `HOME_CARE` | 어린이집·유치원을 다니지 않고 집에서 돌봄 | 가정양육수당, 시간제보육 지원, 시간제보육 보육료 지원 |
| `USES_CHILDCARE` | 어린이집·유치원을 다님 | 영유아보육료, 유아교육비·보육료 추가지원, 누리과정, 청주 차액보육료, 장애아보육료, 연장형 보육료 2건, 유아 무상교육·보육, 방과후 보육료 |

- 화면은 출산하는 분과 배우자를 따로 묻는다 (선택 안 함 / 가입 / 미가입). "직장인" 체크 하나로는 미적용자 출산급여처럼 **미가입이어야 받는 혜택**을 표현할 수 없다.
- **함께 받을 수 없는 혜택은 조건으로 나눈다.** 가정양육수당 원문에 "중복불가서비스: 유아학비(누리과정) 지원, 영유아보육료 지원"이 있어서, 돌봄 방식(집 / 어린이집·유치원)을 묻고 맞는 쪽만 보여준다. 원문으로 정할 수 없는 혜택(부모급여는 집에서는 현금, 어린이집에서는 보육료로 받음, 아이돌봄 등)에는 조건을 붙이지 않는다.
- **답하지 않은 조건으로는 빼지 않는다.** 금액 합계에서는 그런 혜택에 "어린이집·유치원 안 다닐 때"처럼 조건을 표시한다. 확실히 안 맞을 때만 빼고, 뺀 혜택은 이유와 함께 화면 아래에 보여준다.
- 조건을 바꾸면 그 혜택은 다시 "검증 전"이 된다.

## 매일 확인 (수집 + 검토 요약)

코드: `apps/api/src/daily-check/` — 수집(`collect`)과 혜택 검토(`benefit`)는 서로를 모르고, 이 기능이 둘을 차례로 부른다.

- **확인 필요**: 사람이 확인한 뒤로 원본이 바뀜 / 사라짐 / 수집된 적 없는 원본을 가리킴. 이름과 바뀐 필드를 보고서에 적는다 (최대 20건, 나머지는 건수).
- **검증 전**은 건수만 적는다. 매일 새로 생기는 소식이 아니라서 목록으로 늘어놓지 않는다.
- 수집이 실패해도 이전에 저장된 원본으로 검토 요약은 만든다. 검토 요약을 못 만들어도 수집 결과는 보여준다.
- 확인 필요 혜택, 수집 실패, 검토 실패 중 하나라도 있으면 서버 로그에 경고(WARN)로 남긴다.

## 금액

혜택 목록 파일의 `amount`에 적는다. 출생 순위별 금액 계산과 합계는 **브라우저에서** 한다.

```json
"amount": {
  "kind": "voucher",
  "summary": "첫째 200만원, 둘째 이상 300만원",
  "tiers": [
    { "minBirthOrder": 1, "maxBirthOrder": 1, "won": 2000000 },
    { "minBirthOrder": 2, "maxBirthOrder": null, "won": 3000000 }
  ],
  "basis": { "text": "근거가 된 원문 문장", "url": "https://..." }
}
```

- `kind`: `cash`(현금), `voucher`(이용권), `service`(서비스), `wage`(휴가·휴직 때 임금 대신 받는 급여)
- `tiers`: 받는 **총액**을 출생 순위 구간별로 적는다. 첫째부터 빈틈과 겹침 없이 이어지고 마지막 구간은 끝이 없어야 한다 (`maxBirthOrder: null`). 매달 받는 혜택은 받을 수 있는 기간 전체를 더한 값이다 (아동수당 월 10만원 × 96개월 = 960만원).
- 소득·임금에 따라 달라서 정할 수 없으면 `tiers: null`로 두고 `summary`에만 적는다. 합계에서 빠진다.
- 원문에 금액이 없으면 넣지 않는다 (부모급여는 공공 API 원문에 금액이 없어 아직 비워 둠).
- 금액을 바꾸면 그 혜택은 다시 "검증 전"이 된다.

정리한 금액 (2026-11-02, 모두 검증 전):

| 혜택 | 합계에 넣는 금액 | 설명 |
|---|---|---|
| 충북 출산육아수당 | 1,000만원 | 만 6세까지 6번 나눠 지급 (2024년 출생아 기준) |
| 아동수당 | 960만원 | 월 10만원 × 96개월 |
| 가정양육수당 | 620만원 | 월 10만원 × 62개월 (어린이집·유치원을 다니지 않을 때) |
| 첫만남이용권 | 첫째 200만원, 둘째 이상 300만원 | 이용권 |
| 임신·출산 진료비 | 100만원 | 다태아는 더 받음 |
| 고용보험 미적용자 출산급여 | 150만원 | 출산하는 분이 고용보험 미가입일 때 |

## 올해 신청 기간

해마다 공고하는 사업은 혜택 목록 파일의 `applicationPeriod`에 **실제 날짜**로 적는다. 출생일 기준 일정(`schedule`)과는 따로 둔다.

```json
"applicationPeriod": {
  "start": "2026-06-15",
  "end": "2026-12-31",
  "basis": { "text": "신청기한: 2026. 6. 15.(월) ~ 2026. 12. 31.(목)", "url": "https://..." }
}
```

- 기간이 지나도 **혜택은 지우지 않는다.** 다음 해에 다시 열리는 경우가 많아서, 화면에서 표시만 바꾼다.

| 오늘 기준 | 화면 표시 |
|---|---|
| 시작 전 | 올해 신청 6.15(월)부터 |
| 신청 중 (마감까지 30일 넘게) | 올해 신청 12.31(목)까지 |
| 마감 30일 전부터 | 신청 마감 D-N · 12.31(목) (눈에 띄는 색) |
| 마감 당일 | 오늘 신청 마감 |
| 올해 마감됨 | 올해 신청 마감됨 · 내년 공고를 확인해 주세요 (카드를 흐리게) |
| 작년 이전에 마감됨 | 2025년 신청 마감됨 · 올해 공고를 확인해 주세요 (카드를 흐리게) |

- 새해 공고가 나오면 날짜만 바꾼다. 날짜를 바꾸면 그 혜택은 다시 "검증 전"이 된다.

정리한 5건 (2026-11-02): 결혼·출산가정 대출이자(2025.1.1~12.19), 임산부 친환경농산물(2026년 7월), 청소년 미혼 한부모 자립지원(2026.10.1~10.31), 에너지바우처(2026.6.15~12.31), 인플루엔자 국가예방접종(2026.9.21~2027.4.30)

## 대상 묶음

특정 대상만 받는 혜택은 혜택 목록 파일의 `audience`에 묶음을 적는다. 화면에서는 누구나 받는 혜택 아래 **"해당되면 확인하세요"**에 접어서 보여준다.

| 값 | 묶음 |
|---|---|
| `INFERTILITY` | 난임·임신 준비 |
| `MULTI_CHILD` | 다자녀·다태아 |
| `SICK_CHILD` | 아이 건강 (미숙아·질환·발달) |
| `LOW_INCOME` | 기초생활·차상위 등 저소득 |
| `SINGLE_TEEN_PARENT` | 한부모·청소년부모 |
| `DISABILITY` | 장애 |
| `ADOPTION_FOSTER` | 입양·가정위탁 |
| `SPECIAL` | 그 밖의 특정 대상 (보훈, 군 지역, 인구감소지역, 가정 출산, 위기임신 등) |

- 혜택 내용이 아니라 **보여주는 자리**라서, 묶음만 바꾸면 확인 기록을 유지한다 (`sync` 결과에 "대상 묶음만 바뀜"으로 따로 나온다).
- 타임라인에는 영향을 주지 않는다. 일정이 있는 혜택은 묶음이 있어도 타임라인에 나온다.
- 묶음은 원문의 지원대상을 보고 사람이 정한다. 처음 분류(2026-11-02): 60건 묶음, 51건 누구나.
