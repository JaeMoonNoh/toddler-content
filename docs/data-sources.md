# 데이터 출처

혜택 데이터는 공공데이터포털(data.go.kr)의 API 세 개에서 받는다. 인증키는 계정당 하나이고 세 API에 같은 키를 쓴다.
키는 `apps/api/.env`의 `DATA_GO_KR_SERVICE_KEY`에만 둔다 (git 제외).

조사일: 2026-11-02

## 1. 보조금24 (주 출처)

- 기본 주소: `https://api.odcloud.kr/api/gov24/v3`
- `serviceList`: 목록. 서비스명, 지원대상, 선정기준, 지원내용, 신청방법, 신청기한, 소관기관, 수정일시 등
- `serviceDetail`: 상세. 구비서류, 법령, 자치법규, 온라인신청사이트URL 등이 추가됨
- `supportConditions`: 서비스별 대상 조건 코드
- 페이지당 최대 1,000건 → 전체 수집은 엔드포인트별 11번 호출
- 필터: `cond[수정일시::GTE]=20261101000000` 처럼 **수정된 것만** 받을 수 있다 → 매일 변경 감지에 사용

조건 코드 중 우리가 쓰는 것:

| 코드 | 뜻 |
|---|---|
| JA0301 | 예비부모/난임 |
| JA0302 | 임산부 |
| JA0303 | 출산/입양 |
| JA0110, JA0111 | 대상 연령 시작, 끝 |
| JA0411 | 다자녀가구 |
| JA0201~JA0205 | 중위소득 구간 (0~50%, ~75%, ~100%, ~200%, 200% 초과) |

## 2. 복지로 중앙부처 (보완 출처)

- 목록: `https://apis.data.go.kr/B554287/NationalWelfareInformationsV001/NationalWelfarelistV001?callTp=L&srchKeyCode=001&pageNo=1&numOfRows=500`
- 보조금24에 이름으로 검색되지 않는 **부모급여 지원**, **모성보호육아지원(출산전후휴가·육아휴직 급여)** 이 여기에는 있다.

## 3. 복지로 지자체 (보완 출처)

- 목록: `https://apis.data.go.kr/B554287/LocalGovernmentWelfareInformations/LcgvWelfarelist?ctpvNm=충청북도&pageNo=1&numOfRows=500`
- 청주시 항목은 `sggNm`에 "청주시"가 들어간 것. 충북 302건 중 청주 28건.

## 후보를 고르는 방법

1. 지역: 보조금24는 `소관기관명`에 "청주"가 있으면 청주, 정확히 "충청북도"면 충북, `소관기관유형`이 중앙행정기관·공공기관이면 전국.
   복지로 지자체는 `sggNm`이 청주시면 청주, 비어 있으면 충북.
2. 관련성:
   - **강함**: 서비스명에 임신·출산·영유아 관련 단어가 있거나, 임신·출산 코드(JA0301~0303)가 붙어 있으면서 다른 대상 코드가 거의 없는 것
   - **후보**: 임신·출산 코드는 붙어 있지만 대상이 넓고, 지원대상 설명에 관련 단어가 있는 것
3. 같은 혜택이 두 출처에 모두 있으면 이름을 정규화해서 한 줄로 합친다.

결과: [research/2026-11-02-cheongju-candidates.md](research/2026-11-02-cheongju-candidates.md) (155건)

## 주의할 점

- **조건 코드와 생애주기 값은 넓게 붙어 있다.** "누구나 대상"인 서비스(예: 근로·자녀장려금)도 임산부 코드가 Y이고, 휠체어 수선비에도 "영유아"가 붙어 있다. 코드만으로 거르면 3,960건이 나와서 쓸 수 없다. 이름·설명 키워드와 함께 판단하고, 최종 포함 여부는 사람이 정한다.
- **한 출처로는 부족하다.** 보조금24에 부모급여가 없고, 복지로에는 상세 정보(선정기준, 신청기한)가 적다. 두 출처를 함께 받고 같은 혜택끼리 연결해야 한다.
- 금액은 대부분 `지원내용` 문장 안에 있다. 금액을 숫자로 쓰려면 사람이 확인해서 입력해야 한다.

## 변경 감지

코드: `apps/api/src/collect/` — `domain/snapshot-diff.ts`(무엇을 변경으로 보는가), `application/apply-snapshot.use-case.ts`·`collection-policy.ts`(수집 반영 흐름과 정책), `infrastructure/prisma-snapshot.repository.ts`(DB 저장)

| 테이블 | 내용 |
|---|---|
| `SourceItem` | 출처 + 출처 ID별 최신 원본(`payload`), 비교용 지문(`hash`), 목록에서 사라진 시각(`removedAt`) |
| `SourceChange` | 수집 한 번에서 발견한 추가 / 변경 / 삭제. 변경이면 `changedFields`에 `{ field, before, after }` |
| `CollectionRun` | 출처별 수집 실행 기록. 상태, 건수, 오류 |

동작 규칙:

- 출처의 **전체 목록**을 받아 저장된 원본과 비교한다. 보조금24는 `수정일시` 필터로 바뀐 것만 받을 수도 있지만, 삭제는 전체 목록을 받아야 알 수 있어서 하루 한 번 전체를 받는다 (보조금24 호출 22번, 한도 안).
- 지문은 키 순서와 상관없이 같은 내용이면 같게 나오도록 계산한다. **매일 바뀌는 필드는 비교에서 뺀다** (보조금24 `조회수`, 복지로 `inqNum`). 빼지 않으면 매일 수천 건이 "변경"으로 잡힌다.
- **첫 수집은 기준점만 저장**하고 변경 기록은 남기지 않는다.
- 사라졌던 항목이 다시 나타나면 "추가"로 기록한다.
- 받은 항목이 **0건이거나 이전보다 10% 넘게 줄면 수집을 중단**하고 실패로 기록한다. API 장애로 목록이 일부만 왔을 때 대량 삭제로 오인하지 않기 위해서다.

실제 보조금24 데이터 10,942건으로 확인한 결과: 첫 수집 1.1초, 이후 수집 0.3초.

## 수집기

코드: `apps/api/src/collect/infrastructure/sources/` (출처별 fetcher), `cli/` (수동 실행), `scheduling/` (자동 실행)

| 출처 | 클래스 | 한 번에 받는 건수 | 하루 전체 수집 호출 수 (2026-11-02 기준) |
|---|---|---|---|
| 보조금24 | `Gov24Fetcher` | 1,000 | 11 |
| 복지로 중앙부처 | `BokjiroNationalFetcher` | 500 | 1 |
| 복지로 지자체 | `BokjiroLocalFetcher` | 500 | 10 |

- 실행: `pnpm collect` 또는 매일 새벽 4시(한국 시각) 자동 실행.
- 출처는 차례로 수집하고, **한 출처가 실패해도 나머지는 계속한다.** 실패도 `CollectionRun`에 이유와 함께 남는다.
- 같은 수집이 겹치면 나중 것은 건너뛴다.
- 요청은 시간 초과 30초, 5xx·429·네트워크 오류만 최대 2번 재시도한다. 4xx(인증키 오류 등)는 바로 실패한다.
- 목록이 중간에 잘리거나(빈 페이지, 건수 부족), ID 없는 항목이 있으면 그 출처의 수집을 실패로 처리한다. 잘못된 목록으로 삭제가 기록되지 않게 하기 위해서다.
- 공공데이터포털 오류는 HTTP 403 + XML로 오기도 하고, HTTP 200 + XML(`OpenAPI_ServiceResponse`)로 오기도 한다. 둘 다 실패로 본다.
- 오류 메시지와 DB 기록에서 인증키는 `serviceKey=***`로 가린다.

새 출처를 추가하려면 `PagedSourceFetcher`를 상속해 "한 페이지 가져오기"와 "항목 → 원본 변환"만 구현하고, `CollectModule`의 fetcher 목록에 넣는다.

실제 수집 결과 (2026-11-02): 세 출처 16,231건 첫 수집 16초, 바로 다시 수집했을 때 변경 0건 (조회수 무시가 실제 데이터에서도 동작).

## 검토와 게시

코드: `apps/api/src/benefit/` — `domain/benefit.ts`(검토 상태 규칙), `application/`(목록 반영, 검토 대기열, 확인, 게시 목록), `infrastructure/`(목록 파일, DB, 명령, API)

혜택 목록은 `apps/api/data/benefit-catalog.json`에 있다 (조사에서 확정한 112건). 혜택마다 근거가 되는 공공 API 원본을 하나 이상 연결하고, 첫 번째가 대표 출처다.

| 테이블 | 내용 |
|---|---|
| `Benefit` | 사이트에 올리는 혜택. 이름, 지역, 원문 링크, 사람이 마지막으로 확인한 시각(`verifiedAt`) |
| `BenefitSource` | 혜택이 근거로 삼는 원본(출처 + 출처 ID)과, 확인할 때의 원본 지문·내용 |

검토 상태는 저장하지 않고, **확인할 때의 원본과 지금 수집된 원본을 비교해서** 그때그때 정한다. 그래서 수집기는 혜택을 몰라도 되고, 원본이 바뀌었다가 원래대로 돌아오면 자동으로 "확인됨"이 된다.

| 상태 | 뜻 | 사이트 |
|---|---|---|
| 확인됨 | 확인한 뒤로 원본이 그대로 | 게시 |
| 원본 바뀜 | 확인한 뒤로 원본이 바뀜 | 마지막 확인 내용과 확인일로 계속 게시 (`sourceChangedSinceVerified: true`) |
| 확인 전 | 아직 확인하지 않았거나, 확인 뒤에 목록 파일에서 혜택 정보를 고침 | 게시 안 함 |
| 원본 사라짐 | 출처 목록에서 사라짐 (사업 종료일 수 있음) | 게시 멈춤 |
| 원본 없음 | 수집된 적 없는 ID를 가리킴 (목록 파일 오타 등) | 게시 안 함 |

- 원본이 바뀐 혜택을 바로 내리지 않는 이유: 문구 수정처럼 작은 변경도 많아서, 내리면 사이트에서 혜택이 자주 사라졌다 나타난다. 대신 확인일을 그대로 보여줘서 언제 기준 정보인지 알 수 있게 한다.
- 목록 파일에 문제가 하나라도 있으면 아무것도 반영하지 않는다. 목록에서 빠진 혜택은 DB에서 지우지 않고 알려만 준다.
- 사라졌거나 없는 원본은 확인할 수 없다. 목록 파일에서 연결을 고치거나 혜택을 빼야 한다.
